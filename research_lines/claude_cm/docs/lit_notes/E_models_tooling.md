# E. Models & tooling survey for per-token MoE routing logging (customer-service agent, RTX 5090 / WSL2)

Survey date: 2026-09-02. Every number below was read from a page fetched during this survey (URL given per cluster). Where a number could not be verified it is marked "not verified". VRAM figures marked "est." are computed from the Hugging Face API `safetensors.total` parameter counts (2 bytes/param for bf16; ~0.6 bytes/param as a rule of thumb for NF4/INT4 incl. unquantized embeddings/norms/routers) and are estimates, not measurements. KV-cache and activation memory are extra.

Toolchain versions observed on PyPI on 2026-09-02 (https://pypi.org/pypi/<pkg>/json): torch 2.13.0 (2026-07-08), transformers 5.16.1 (2026-08-26), bitsandbytes 0.50.2 (2026-08-27), vllm 0.28.0 (2026-08-26), sglang 0.5.18 (2026-08-21), triton 3.8.0, kernels 0.16.1, gptqmodel 7.3.6, accelerate 1.14.0, safetensors 0.8.0, litellm 1.99.0, tau2 2.4.0. `tau-bench` is not on PyPI (install from source).

### 1.2 Notes per model (sources)

**OLMoE-1B-7B (0924 / 0125 Instruct).** Config: 16 layers, 64 experts, `num_experts_per_tok` 8, `norm_topk_prob` false, `router_aux_loss_coef` 0.01 (https://huggingface.co/allenai/OLMoE-1B-7B-0125-Instruct/raw/main/config.json). Card: Apache-2.0, SFT+DPO+RLVR, paper https://arxiv.org/abs/2409.02060 (https://huggingface.co/allenai/OLMoE-1B-7B-0125-Instruct). The paper has a full routing-analysis section: router saturation ("after 1% of pretraining ... up to ~60% of routing to the top-8 activated experts has already saturated", ~80% by 40%), expert co-activation ("no strong co-activation among experts in one layer, with only few exceptions"), domain specialization (layer-0 expert nearly 100% on arXiv tokens; C4 near the 12.5% baseline), vocabulary specialization (experts for punctuation, Devanagari, etc.) (https://arxiv.org/html/2409.02060). Tool calling is not documented on either card. 0924 evals on card: MMLU 51.9, IFEval loose 48.1 (https://huggingface.co/allenai/OLMoE-1B-7B-0924-Instruct). transformers: `OlmoeSparseMoeBlock.gate` (`OlmoeTopKRouter`, weight `nn.Parameter(num_experts, hidden)`), softmax-then-topk, `_can_record_outputs["router_logits"] = OutputRecorder(OlmoeTopKRouter, index=0)`, experts decorated `@use_experts_implementation` (https://raw.githubusercontent.com/huggingface/transformers/main/src/transformers/models/olmoe/modeling_olmoe.py).

**gpt-oss-20b.** Card: "21B parameters with 3.6B active", "run within 16GB of memory", Apache-2.0, "native capabilities for function calling, web browsing, Python code execution, and Structured Outputs", must use harmony format (chat template applies it) (https://huggingface.co/openai/gpt-oss-20b). Config: 24 layers, 32 local experts, 4 per token, alternating sliding(128)/full attention, `quantization_config.quant_method = "mxfp4"` with `modules_to_not_convert` including `model.layers.*.mlp.router` (https://huggingface.co/openai/gpt-oss-20b/raw/main/config.json). HF API: 20.91B params, 19.11B stored as U8 (MXFP4) + 1.80B BF16. Memory: HF blog says "~48GB of VRAM" if unpacked to bf16, MXFP4 ~16 GB; requires transformers >= 4.55.1, Triton >= 3.4, `accelerate`, `kernels` (https://huggingface.co/blog/welcome-openai-gpt-oss). MXFP4 doc: NVIDIA compute capability >= 7.5, kernels auto-pulled from `kernels-community/triton_kernels`, model on disk 13.8 GB (https://huggingface.co/docs/transformers/main/en/quantization/mxfp4). OpenAI cookbook: "MXFP4 is supported in Hopper or later architectures ... as well as the latest RTX 50xx family of consumer cards" (https://developers.openai.com/cookbook/articles/gpt-oss/run-transformers). Router: `GptOssTopKRouter` computes `router_logits = F.linear(...)`, then `topk` then `softmax` over the top-k values (i.e. probabilities are renormalized over the selected experts; full-distribution probs must be recomputed from logits), `_can_record_outputs["router_logits"] = OutputRecorder(GptOssTopKRouter, index=0)`; `GptOssMLP` is decorated `@use_kernel_forward_from_hub("MegaBlocksMoeMLP")` (https://raw.githubusercontent.com/huggingface/transformers/main/src/transformers/models/gpt_oss/modeling_gpt_oss.py). The MXFP4 integration replaces only `GptOssExperts` with `Mxfp4GptOssExperts` and rewrites `GptOssMLP.forward` to compute `router_logits = nn.functional.linear(hidden_states, self.router.weight, self.router.bias)` then `routing(router_logits, self.router.top_k)` (https://raw.githubusercontent.com/huggingface/transformers/main/src/transformers/integrations/mxfp4.py) -- so under MXFP4 the router *module's* forward is not called; hook `GptOssMLP` (or read `router_logits` via a hook on the `router` Linear's weight computation is not possible) -- practical option: register a forward hook on `model.layers[i].mlp` and recompute logits from `mlp.router.weight/bias` on the hook's input, or hook `GptOssTopKRouter` only in the non-MXFP4 path. Notes in transformers docs: "SDPA is not supported because attention sinks require direct access to the full attention logits"; use eager, Flash or Flex attention (https://huggingface.co/docs/transformers/main/en/model_doc/gpt_oss). Third-party routing analyses on gpt-oss-20b: RouterInterp (ICLR 2026; SAE features predict routing "77% higher accuracy than prior methods"; Superposed Specialisation Hypothesis) (https://iclr.cc/virtual/2026/10016067); counterfactual "misrouting" study covering Qwen3-30B-A3B, GPT-OSS-20B, DeepSeek-V2-Lite and OLMoE-1B-7B (https://arxiv.org/abs/2605.07260); "Does the same token mean the same state?" uses gpt-oss and Qwen3-MoE routing states during decoding (https://arxiv.org/abs/2606.22798).

**Qwen3-30B-A3B / -Instruct-2507.** Card: 30.5B total / 3.3B activated (29.9B non-embedding), 48 layers, 128 experts / 8 activated, Apache-2.0, native context 262,144 (2507), transformers >= 4.51.0 required, "We recommend using Qwen-Agent to make the best use of agentic ability" (https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507, https://huggingface.co/Qwen/Qwen3-30B-A3B). ### 1.3 Ranking

(a) Fast iteration (fits in bf16, native router-logit capture, small layer x expert grid):
1. OLMoE-1B-7B-0125-Instruct -- 13.8 GB bf16, 16 x 64 routing grid, ORL native, authors' routing analysis to compare against, fully open.
2. Granite-3.1-3B-A800M-Instruct -- 6.6 GB, tool-calling trained, but logits need hooks (index 2) and softmax-after-top-k means the full-distribution probabilities must be recomputed from logits.
3. Granite-4.0-H-Tiny -- 13.9 GB bf16, tool calling, shared expert; hybrid Mamba-2 needs `mamba-ssm`/`causal-conv1d` builds on sm_120 (risk), hooks only.
4. gpt-oss-20b (MXFP4) -- ~16 GB VRAM, native ORL in the eager path, but the MXFP4 fast path bypasses the router module (see 2.3) and uses a top-k-then-softmax router.
5. DeepSeek-V2-Lite-Chat -- 31.4 GB bf16 is too tight; needs quantization, hooks only.

(b) Realistic agent behavior (instruction/tool-use quality):
1. gpt-oss-20b -- native function calling, agentic post-training, fits in MXFP4.
2. Qwen3-30B-A3B-Instruct-2507 -- strong agentic model, but 61 GB bf16; on 32 GB it must be 4-bit, and bitsandbytes cannot quantize the fused experts in transformers v5 (3.3) -> realistic paths are vLLM+AWQ/GPTQ with `--enable-return-routed-experts` (IDs only) or CPU offload in transformers.
3. Qwen3.6-35B-A3B / Qwen3.5-35B-A3B -- newest, same quantization problem, multimodal wrapper adds complexity.
4. Nemotron-3-Nano-30B-A3B -- agentic-reasoning tuned, but 63 GB bf16 + Mamba + hooks-only.
5. Trinity-Mini -- function calling per card, 52 GB bf16, needs 4-bit.
6. Granite-4.0-H-Tiny -- tool calling in a 7B/1B package that fits bf16.

## 2. Routing extraction in practice

### 2.1 `output_router_logits=True` in transformers (v5.16)

- Supported (config flag + `MoeCausalLMOutputWithPast.router_logits`): Qwen3Moe, Qwen3.5-MoE, Qwen2Moe, OLMoE, Mixtral, PhiMoE, GptOss, Jamba, Afmoe, GraniteMoe/GraniteMoeHybrid (config flag exists, but the router class is not registered for recording, see below). Docstring for every one of these: "router_logits (tuple(torch.FloatTensor), optional ...) Tuple of torch.FloatTensor (one for each layer) of shape (batch_size, sequence_length, num_experts). Raw router logits (post-softmax) that are computed by MoE routers" and the forward-arg note "output_router_logits ... should not be returned during inference" (https://huggingface.co/docs/transformers/main/en/model_doc/qwen3_moe, .../gpt_oss, .../phimoe, .../granitemoe, .../jamba, .../afmoe). The docstring wording "post-softmax" is misleading: in the sources the recorded tensor is the pre-softmax `router_logits` (index 0 of the router's return), and because routers flatten the batch (`hidden_states.reshape(-1, hidden_dim)`, OLMoE source) the per-layer tensor is actually `(batch*seq, num_experts)`; reshape it yourself.
- Not supported natively: DeepseekV2 (forward returns `CausalLMOutputWithPast`; router logits discarded), NemotronH (no flag), GraniteMoe/GraniteMoeHybrid (`_can_record_outputs` lists only hidden_states/attentions).
- Mechanism (`OutputRecorder` / `_can_record_outputs`): a decorator computes `recordable_keys = {f"output_{k}": kwargs.get(f"output_{k}", getattr(self.config, f"output_{k}", False)) ...}`; when any is True, `maybe_install_capturing_hooks` installs forward hooks on modules whose class matches `OutputRecorder(target_class, index=...)`, appends `output[index]` per call, and attaches `outputs[key] = tuple(collected_outputs[key])`; hooks are *not* removed afterwards, only deactivated via a context variable (https://raw.githubusercontent.com/huggingface/transformers/main/src/transformers/utils/output_capturing.py). Consequence: the flag only works when the Python `forward` of the router class runs.
- `generate()`: `GenerateDecoderOnlyOutput` has only `sequences, scores, logits, attentions, hidden_states, past_key_values` -- no router field (https://raw.githubusercontent.com/huggingface/transformers/main/src/transformers/generation/utils.py). Issue #31722 ("how to generate router_logits in moe models using model.generate()?") ended with maintainer gante: "Forwarding MoE-specific outputs is not yet enabled in `generate`, but we'd gladly accept a PR for it!" (https://github.com/huggingface/transformers/issues/31722, comments via GitHub API, 2024-08-02). So for decoding you need hooks or your own decode loop.

### 2.2 Forward hooks (recommended for both prefill and decode)

Register `register_forward_hook` on the router module (or on the MoE block and read the tuple) and record per call: layer index, `output[idx_logits]` (fp32 softmax gives full probabilities), top-k indices and top-k weights. Module paths in transformers v5.16 (`model.model.layers[i]...`):

| Family | Path to router | Return tuple (index of raw logits) | Softmax order |
|---|---|---|---|
| OLMoE | `.mlp.gate` (`OlmoeTopKRouter`) | (logits, scores, indices) (0) | softmax -> topk; renorm only if `norm_topk_prob` |
| Qwen3-MoE / Qwen2-MoE / Qwen3.5-MoE | `.mlp.gate` (`Qwen3MoeTopKRouter` etc.) | (logits, scores, indices) (0) | softmax -> topk (+renorm) |
| Mixtral | `.mlp.gate` (`MixtralTopKRouter`) | (logits, scores, indices) (0) | softmax -> topk |
| gpt-oss | `.mlp.router` (`GptOssTopKRouter`) | (logits, scores, indices) (0) | topk -> softmax over k |
| PhiMoE | `.mlp.gate`-style `PhimoeTopKRouter` (nn.Linear subclass) | (logits, weights, selected) (0) | SparseMixer |
| DeepSeek-V2 | `.mlp.gate` (`DeepseekV2TopkRouter`) | (logits, weights, indices) (0) | softmax -> topk; layer 0 dense |
| GraniteMoe / GraniteMoeHybrid | `...router` (`GraniteMoeTopKRouter`) | (index, weights, logits) (2) | topk -> softmax |
| NemotronH | not fetched; hook the MoE block | – | `norm_topk_prob`, `routed_scaling_factor` 2.5 |

Practical notes from the sources above: (i) during decoding with KV cache each forward processes one token, so the hook fires once per layer per step with shape `(batch, num_experts)`; you must stamp step/position yourself; (ii) router input is flattened, so with batch > 1 rows are `(b*s)` ordered; (iii) `experts_implementation` ("eager", "batched_mm", "grouped_mm"; default "grouped_mm" when supported) only changes the experts kernel and receives `top_k_index/top_k_weights` from the router, so hooks on the router are unaffected (https://raw.githubusercontent.com/huggingface/transformers/main/src/transformers/integrations/moe.py, https://huggingface.co/docs/transformers/main/en/main_classes/model).

### 2.3 Pitfalls

- **Hub kernels (`use_kernels=True`) bypass the router.** Issue #40104: with kernels installed `out.router_logits` is `None` for `GptOssForCausalLM`; reporter switched to hooks, maintainer ArthurZucker: "yes your hack works well" (https://github.com/huggingface/transformers/issues/40104 + API comments). Cause: `GptOssMLP` is `@use_kernel_forward_from_hub("MegaBlocksMoeMLP")`, so the fused kernel replaces the whole MLP forward (router included). Leave `use_kernels` unset (opt-in; global off switch `USE_HUB_KERNELS=0`) (https://huggingface.co/docs/transformers/main/en/kernel_doc/loading_kernels).
- **MXFP4 path for gpt-oss**: `Mxfp4GptOssExperts` replaces experts and the MLP forward computes logits with `nn.functional.linear(hidden_states, self.router.weight, self.router.bias)` directly -- `GptOssTopKRouter.forward` is not called, so `OutputRecorder`/router hooks see nothing. Hook `layers[i].mlp` (forward pre-hook on its input) and recompute `logits = x @ router.weight.T + router.bias`, top-4, softmax-over-k, exactly as the model does (https://raw.githubusercontent.com/huggingface/transformers/main/src/transformers/integrations/mxfp4.py). The router is deliberately excluded from quantization (`modules_to_not_convert`).
- **Attention implementation**: gpt-oss cannot use SDPA (attention sinks) -> eager/flash/flex (https://huggingface.co/docs/transformers/main/en/model_doc/gpt_oss); FA3 kernel was "tested on Hopper" (https://huggingface.co/blog/welcome-openai-gpt-oss). Hooks are independent of attention backend.
- **KV cache / `logits_to_keep`**: unrelated to router hooks; `logits_to_keep` only truncates LM-head logits.
- **`output_router_logits` is per-forward only**; multi-step generation discards it (2.1).
- **Docstring says "(post-softmax)"** but code records pre-softmax logits; compute softmax in fp32 yourself (router code uses `dtype=torch.float`).

### 2.4 vLLM and SGLang

- **vLLM**: engine arg `--enable-return-routed-experts` ("Whether to return routed experts.", default False) (https://docs.vllm.ai/en/stable/configuration/engine_args/; source `vllm/config/model.py`: `enable_return_routed_experts: bool = False`). Added by PR #28284 "[Feature] Support recording expert indices for rollout router replay" (merged 2026-01-12, GitHub API). Output lands in `CompletionOutput.routed_experts: np.ndarray | None  # [seq_len,layer_num,topk]` (https://raw.githubusercontent.com/vllm-project/vllm/main/vllm/outputs.py). It returns **top-k expert ids only, not probabilities**. RFC #38079 (2026-03) documents that the current implementation uses shared memory + file locks with per-step GPU->CPU sync and proposes per-request opt-in via `vllm_xargs: {"return_routed_experts": true}`; it also reports a period where capture silently returned zeros (https://github.com/vllm-project/vllm/issues/38079). The older forum answer "vLLM does not natively support returning router selections" predates this (https://discuss.vllm.ai/t/can-vllm-return-expert-selection-info-to-support-routing-replay/1742). EPLB (`--enable-eplb`, `--eplb-config '{"log_balancedness": true, ...}'`) only logs aggregate load (avg/max tokens per expert), no per-token data (https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/).
- **SGLang**: `--expert-distribution-recorder-mode` with choices `stat | stat_approx | per_pass | per_token` (server_args.py: `Optional[Literal["stat", "stat_approx", "per_pass", "per_token"]]`), `--expert-distribution-recorder-buffer-size`; `--enable-expert-distribution-metrics` was removed in favor of `--expert-balancedness-report-mode {off,server_log,prometheus,both}` (https://raw.githubusercontent.com/sgl-project/sglang/main/python/sglang/srt/server_args.py). HTTP endpoints `/start_expert_distribution_record`, `/stop_expert_distribution_record`, `/dump_expert_distribution_record` (https://raw.githubusercontent.com/sgl-project/sglang/main/python/sglang/srt/entrypoints/http_server.py). `per_token` uses `_DetailSinglePassGatherer` which records `topk_ids` per token per layer plus input ids/positions and dumps `expert_distribution_recorder_{timestamp}_{rank}.pt` into `SGLANG_EXPERT_DISTRIBUTION_RECORDER_DIR` (https://raw.githubusercontent.com/sgl-project/sglang/main/python/sglang/srt/eplb/expert_distribution.py). Again ids only, no router probabilities.
- Related: RouteScan (2026) audits MoE safety from GPU-thread telemetry of expert modules during prefill (AUROC > 0.91), showing routing side-channels carry task information (https://arxiv.org/abs/2605.24817).

## 3. Environment (RTX 5090 / sm_120, WSL2, Python 3.12, ~15 GB RAM)

- **PyTorch**: sm_120 needs a binary "built with CUDA 12.8+" (ptrblck: "Install any stable or nightly PyTorch binary built with CUDA 12.8+ from our install matrix to support your Blackwell GPU"; PyTorch 2.7 was the first) (https://discuss.pytorch.org/t/pytorch-support-for-sm-120/222119). Current stable torch 2.13.0 (2026-07-08, Python >= 3.10, cp312 wheels) (https://pypi.org/project/torch/). The wheel index for 2.13.0 offers `cu126`, `cu129`, `cu130` (no `cu128` build for 2.13.0; checked https://download.pytorch.org/whl/<cuNNN>/torch/), so use `pip install torch --index-url https://download.pytorch.org/whl/cu130` (or cu129); cu126 has no Blackwell kernels.
- **bitsandbytes 0.50.2** (2026-08-27; torch >= 2.4): PyPI wheels are built for CUDA 12.8 with targets "sm70 ... sm90, sm100, sm120" and CUDA 13.0-13.2 with "sm75 ... sm100, sm120"; the 11.8-12.6 builds stop at sm90. NF4/FP4 need CC 6.0+, LLM.int8 7.5+ (https://huggingface.co/docs/bitsandbytes/main/en/installation). 0.50 release notes: "4-bit inference is up to 4x faster ... across Turing through Blackwell", CUDA 13 support (https://github.com/bitsandbytes-foundation/bitsandbytes/releases). **Critical MoE caveat**: transformers v5 stores experts as fused 3-D `nn.Parameter` (`OlmoeExperts`, `Qwen3MoeExperts`, `MixtralExperts` ...) and bitsandbytes only replaces `nn.Linear`, so `load_in_4bit` silently leaves the experts in full precision (issue #1849: Qwen3-30B-A3B stayed at 55.60 GB instead of 15.09 GB) (https://github.com/bitsandbytes-foundation/bitsandbytes/issues/1849); the fix PR #1965 "Add Experts4bit for 4-bit quantization of fused MoE experts" is still **open** (created 2026-06-05; GitHub API). Practical consequence on 32 GB: prefer models that fit in bf16, gpt-oss MXFP4, or pre-quantized AWQ/GPTQ checkpoints served by vLLM.
- **GPTQ / AWQ**: AutoAWQ is archived (2025-05-11; "officially deprecated", last tested torch 2.6 / transformers 4.51.3), successor is vllm-project/llm-compressor (https://github.com/casper-hansen/AutoAWQ). GPTQModel 7.3.6 (2026-08-31) lists a "Swordfish Blackwell (>= sm100) GPTQ/AWQ kernel", Marlin/Exllama/Triton/Torch backends, MoE support ("Qwen 2/3/3.5/3.8 (Next/MoE)", Mixtral, `Moe.Routing`/`FailSafe`) and HF integration; explicit sm_120 support is not stated on the README (https://github.com/ModelCloud/GPTQModel). vLLM has active sm_120 work (e.g. PR #50288 NVFP4 KV cache for RTX 5090).
- **MXFP4 for gpt-oss on 5090**: transformers doc requires CC >= 7.5, `accelerate`, `kernels`, Triton >= 3.4 (bundled with torch >= 2.8) (https://huggingface.co/docs/transformers/main/en/quantization/mxfp4); OpenAI cookbook: "RTX 50xx family" supported (https://developers.openai.com/cookbook/articles/gpt-oss/run-transformers). Early releases errored with "only supported on GPUs with compute capability >= 9.0" until PR #39940; users needed transformers from main, triton 3.4, triton_kernels (https://huggingface.co/openai/gpt-oss-20b/discussions/61). bf16 fallback is ~48 GB and does not fit.
- **WSL2 memory**: `.wslconfig` `[wsl2]` `memory` defaults to "50% of total memory on Windows", `swap` to "25% of memory size on Windows rounded up to the nearest GB", `swapFile` default `%Temp%\swap.vhdx`; changes need `wsl --shutdown` (8-second rule); `[experimental] autoMemoryReclaim=gradual|dropCache` (https://learn.microsoft.com/en-us/windows/wsl/wsl-config). With ~15 GB visible, raise `memory=` (and `swap=`) in `%UserProfile%\.wslconfig`.
- **CUDA on WSL2**: install only the Windows NVIDIA driver ("Do not install any Linux display driver in WSL"); inside WSL install `cuda-toolkit-12-x` only, never the `cuda`/`cuda-drivers` metapackages; `libcuda.so` is stubbed from `/usr/lib/wsl/lib`; pinned memory is limited (https://docs.nvidia.com/cuda/wsl-user-guide/index.html).
- **Loading large safetensors with little RAM**: transformers creates the skeleton on the meta device ("maximum memory usage is only the size of the model"), loads shards in parallel, and for MoE "memory usage is the model size plus the number of experts on one layer" during dynamic weight conversion (https://huggingface.co/docs/transformers/main/en/models). `from_pretrained(..., disable_mmap=None|True|False)` controls memory-mapped safetensors loading; `device_map="cuda"`/`"auto"`, `max_memory`, `offload_folder` available (https://huggingface.co/docs/transformers/main/en/main_classes/model). Older issue #28476 reports >7 GB CPU RAM to load a 4 GB model to GPU (https://github.com/huggingface/transformers/issues/28476). Keep the HF cache on the Linux ext4 filesystem (not /mnt/c) and pass `device_map="cuda"` so shards go straight to the GPU.

## 5. Recommendation

**Start with two models, in this order.**

1. **allenai/OLMoE-1B-7B-0125-Instruct** for building and validating the logging pipeline. It fits on the 5090 in bf16 (13.8 GB, leaving room for KV cache and full-distribution logging), has a compact 16-layer x 64-expert routing grid with top-8, its transformers implementation exposes `router_logits` natively (`OutputRecorder(OlmoeTopKRouter, index=0)`) *and* has a clean `layers[i].mlp.gate` hook point that returns `(logits, scores, indices)`, and the OLMoE paper provides published baselines (router saturation, co-activation, domain and vocabulary specialization) to sanity-check your statistics. Weakness: no documented tool-calling training, so use it for prefill/decode routing-shift experiments with prompted (JSON) tool use rather than as the headline agent.

2. **openai/gpt-oss-20b** as the realistic customer-service agent. It is the only candidate with native function calling that fits on 32 GB (MXFP4, ~16 GB VRAM; bf16 fallback ~48 GB does not fit), is Apache-2.0, and is the model on which the most recent third-party routing interpretability work was done (RouterInterp, misrouting study). Concrete plan: `pip install torch --index-url .../cu130`, transformers >= 5.16, `kernels`, triton >= 3.4; do **not** pass `use_kernels=True`; because the MXFP4 fast path computes router logits inside the rewritten `GptOssMLP.forward` without calling `GptOssTopKRouter`, register a forward pre-hook on `model.model.layers[i].mlp` and recompute `logits = x @ router.weight.T + router.bias`, `topk(4)`, softmax-over-k (mirroring the model), plus a full-distribution softmax for your metrics; use `attn_implementation="eager"` (no SDPA) for short dialogues; drive it with tau2-bench (retail/airline/telecom) through LiteLLM (`hosted_vllm/` if served by vLLM, or a thin OpenAI-compatible wrapper around your hooked transformers loop, which you need anyway to log decode-time routing).

**Fallbacks.** If gpt-oss's agent quality is insufficient, use **Qwen3-30B-A3B-Instruct-2507** served by vLLM from a community AWQ/GPTQ 4-bit checkpoint with `--enable-return-routed-experts` (gives `[seq_len, layer, topk]` expert ids per token, no probabilities), or run it in transformers with `device_map="auto"` CPU offload (slow) -- transformers+bitsandbytes 4-bit is currently blocked for fused experts (bnb #1849 / PR #1965 open). **Granite-4.0-H-Tiny** is a second bf16-fitting tool-calling model, but its router logits must be hooked (index 2, softmax-after-top-k) and its Mamba-2 layers need kernel builds on sm_120. Avoid Jamba-Mini, Llama-4-Scout, GLM-4.5-Air and Kimi-K2 on this hardware.
