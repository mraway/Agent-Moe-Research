## 0. 一页结论

1. **代码窗口的 token 类别构成与 routine 有明显差别**：code 窗口 15.6% 空白/换行、18.5% 代码符号、
   7.8% 代码关键字，routine 分别是 2.0% / 7.3% / 1.5%。这与 FCM 报告"按 T 规则代码窗口比 routine
   更少结构化"并不矛盾——T 规则把纯换行/缩进 token 判为 prose，同时把 routine 的句号、逗号、数字判为
   structured（§1.4 给出逐条对照）。**盲区不是"代码没有形态差异"。**
2. **一旦按 token 类别取条件，代码的每 token 路由偏移几乎消失，其他域不会**：对 routine 的类条件质心的
   JS（层 5–15 均值）中位数，held-out routine 0.0919、code 0.0990（1.08×）、其他域 drift 0.1356（1.47×）；
   分域最高的 general_knowledge 0.1606、fiction 0.1581、poetry 0.1491，最低的 legal_analysis 0.1067。
3. **routine 的路由高度由 token 身份决定（近似上下文无关）**：同一 token id 在 routine 内部的
   within-id JS 中位 **0.0172**，而不同 token id 的质心之间是 **0.1696**（约 10×）。因此窗口签名基本上
   是"词袋签名"。
4. **但代码不是"用 routine 的 token id 做上下文无关的路由"**：code 中共享 id 的 token 相对 routine 的
   id 质心偏离 0.0449（held-out routine 0.0178，2.5×），只有 45.0% 落在该 id 在 routine 内 q90 散布之内
   （held-out routine 89.1%）。所以 **假设一（"代码由 routine token id 近上下文无关地路由"）被否定**。
5. **决定性的是假设二：连代码的新 token 也像 routine token 一样路由**。code 窗口 39.8% 的 token 是
   routine 解码里从未出现过的 id——与其他域 drift 的 38.4% **几乎相同**（不是代码更"复用"routine 词表）。
   但这些**新 token 到最近 routine 类质心的 JS 中位数：code 0.0853，其他域 drift 0.1284，
   held-out routine（对照）0.0764**。`SELECT` / `def` / ``` ``` `` / `const` / 缩进落进 routine 自己的
   JSON 工具调用符号与标点所占的专家区域；诗与散文的新词则落到 routine 几乎不用的专家上。
6. **在 CAND-A 的几何里，代码的位移和别人一样大，只是落在 routine 方差最大的方向上**（w=8、层 5–15、
   routine-fit 白化）：原始入选率均值位移范数 code **3.34**，cooking 3.82、fiction 4.36、
   general_knowledge 3.96、mathematics 3.46、poetry 4.33、legal 2.19、travel 2.48——**代码并不比别人动得少**。
   但沿该方向的 routine 有效标准差 code **0.198** vs 其他域 0.056–0.107；于是 z 空间位移范数
   code **16.9** vs fiction 57.4 / general_knowledge 71.3 / poetry 56.7 / math 34.4 / cooking 37.2 /
   legal 23.1 / travel 23.2（held-out routine 1.93）。g1 中位数：code 886，routine-fit 中位 621、q90 996。
7. **那些高方差方向就是 routine 自己的 JSON/工具调用符号方向**：code 位移最大的 15 个 (层, 专家) 维里
   13 个的"routine 内最常用它的 token 类"是 `code_symbol`；在这些维上 routine 的 prose-only 窗口均值
   0.09–0.26，含符号/换行 token 的窗口均值 0.48–0.64（36.2% 的 routine w=8 窗口含至少一个这类 token）。
   代码位移的 **62.6%** 平方质量落在 routine 方差最高十分位的维上，其他域是 28.8%–51.7%
   （最接近的 51.7% 正是第二难的 legal_analysis）。
8. **答案**：不是"上下文无关"，也不是"代码没有形态"，而是——**代码把 router 推向 routine 自身在客服
   工具调用 JSON 上来回摆动的那条高方差轴，位移幅度与其他域相当，但被 routine 自己的方差淹没**；
   并且代码的新 token 天然落进这条轴。诗/法条/知识文的位移落在 routine 几乎不动的低方差专家上，
   所以同样的白化把它们放大、把代码压平。

## 1. 方法

### 1.1 区域定义

| 区域 | 定义 | trace 数 | token 数 |
|---|---|---|---|
| ROUTINE（全体） | clean + benign_control 的全部解码 token（B1+B2） | 240 | 23,903 |
| routine-fit | 上面按 `trace_id` 排序后的偶数位 trace（拟合类质心 / id 质心 / 白化） | 120 | 11,979 |
| routine-held | 奇数位 trace（**对照组**，从不参与拟合） | 120 | 11,924 |
| CODE 窗口 | 8 条 `domain=='programming'` drift 的 `product_onset .. min(+48, T)` | 8 | 384 |
| OTHER-DRIFT 窗口 | 51 条非 programming drift 的同样窗口，按域分组 | 51 | 2,378 |

全部 360 条 core trace 共 41,702 个解码 token。锚点敏感性（evidence_onset 变体）见 §7.3：8 条中 5 条
两锚点差 ≤ 9 token，全部指标变化 ≤ 0.010（JS）/ ≤ 25（g1），**结论不依赖锚点选择**。

### 1.2 token 类别规则（按解码文本，`Ġ`→空格、`Ċ`→换行）

按顺序判定：`whitespace`（strip 后为空）→ `code_symbol`（含 `{}[]()<>=_|\/*&^~\`;$#@+` 中任一字符）→
`code_keyword`（大写 SQL 关键字集合，或小写编程关键字集合）→ `punctuation`（无字母数字）→
`number`（有数字无字母）→ `fragment`（纯字母且紧接前一个以字母数字结尾的 token，即真正的词内延续）→
`word` → `other`。`fragment/word` 的"纯文本版"（只看前导空格）作为敏感性同时记录，见 §2.2。

**已知缺陷（如实记录）**：`code_keyword` 类被英语词污染——routine-fit 的 168 个该类 token 里，
` return` 49、` this` 35、` OR` 16、` CASE` 16、`CASE` 12、` new` 9 占绝大多数（` OR`/` CASE`/`ON`/`IN`/
`UPDATE` 来自知识库正文与协议文本）。因此"routine 有 1.5% 代码关键字"不应读成"routine 在写代码"。

### 1.3 路由距离

每个 token 的 router softmax 是 [16, 64]。对某个参照分布（类质心 / 全局质心 / token-id 质心）逐层算
Jensen-Shannon 散度（以 2 为底，落在 [0,1]），再取层 5–15（CAND-A 的层带）的均值。质心一律只由
**routine-fit** 估计。

### 1.4 与 FCM"代码比 routine 更少结构化"的关系（不是矛盾）

FCM 的 T 规则（`src/research_v2/scorers/fcm.py::structured_surface`）先 `strip(" ")`，因此纯换行/缩进
token 走不到符号分支，被判为 **prose**；同时它的 `SOFT_CHARS = ":,.-_/#*+0123456789"` 使 routine 里的
句号、逗号、数字被判为 **structured**。本文的类别规则把这两类分开，于是同一批窗口给出相反的方向：

| 规则 | routine 结构化/符号占比 | code 窗口 |
|---|---|---|
| FCM T 规则（窗口级 ≥4/8） | 20.7%（B1 拟合侧）/ 24.4%（B2 拟合侧）的窗口 | 12.2% / 19.6% 的窗口 |
| 本文 token 级 `code_symbol` | 7.3% 的 token | 18.5% 的 token |
| 本文 token 级 `code_symbol + whitespace` | 9.3% | 34.1% |

两者都对，只是量的不是同一件事。**这也说明"用文本形态条件化"为什么救不了代码**：真正把 routine 变
"结构化"的是散在散文里的句号/数字，而真正把代码变结构化的是换行、缩进与括号。

routine 内部近似上下文无关（1/10），但代码的共享 id token 偏离 routine 的 id 质心 2.5 倍、只有 45% 落在

### 4.1 上下文残差是"相干"的，且方向与其他域正交

残差 = token 路由 − 该 id 的 routine 质心（层 5–15，704 维）。相干度 = ‖平均残差‖ / 平均‖残差‖：

| 区域 | n | 平均‖残差‖ | ‖平均残差‖ | 相干度 | 与平均残差的中位余弦 |
|---|---|---|---|---|---|
| routine-held | 8,998 | 0.1782 | 0.0048 | **0.027** | 0.030 |
| CODE | 129 | 0.3213 | 0.1477 | **0.460** | 0.475 |
| 其他域 drift | 1,029 | 0.3359 | 0.1196 | 0.356 | 0.343 |
| od:cooking | 127 | 0.3409 | 0.2199 | 0.645 | 0.679 |
| od:fiction | 154 | 0.3665 | 0.2244 | 0.612 | 0.667 |
| od:legal_analysis | 139 | 0.2870 | 0.0856 | 0.298 | 0.337 |

余弦：cos(code, other-drift) = **−0.041**，cos(code, routine-held) = −0.308，cos(other, routine-held) = −0.038。

## 9. 对检测器的含义（陈述，不是提案）

本透镜把"代码盲区"从"代码的路由不动"改写成一个可测量的量：**位移方向上的 routine 方差**。
一个能看见代码的检测器必须测量的是"位移相对于**该方向**的 routine 波动"，而 CAND-A 的逐维标准化
恰恰把 routine 在自己 JSON 工具调用轴上的巨大摆动（那几个专家的 sd ≈ 0.30–0.37，接近 [0,1] 上的
伯努利上限）当成噪声预算发给了代码。等价的三种表述：

- 代码把 routine **已经在用**的专家从 ~0.59（含符号窗口）推到 ~0.87；诗与散文把 routine **几乎不用**的
  专家从 ~0.03 推到 ~0.6。前者的信噪比被 routine 自身的形态混合摊薄，后者没有。
- 代码的新 token（`SELECT`/`def`/```/缩进）到最近 routine 类质心的距离 0.0853，只比 routine 自己的
  token（0.0764）远 12%；其他域的新 token 是 0.1284（+68%）。**词表新颖性在代码上不产生路由新颖性。**
- 代码的上下文残差是相干的（相干度 0.460，中位余弦 0.475）且与其他域正交（cos = −0.041），
  所以它**不会**被任何"以其他域 drift 校准出来的方向"捕捉到。

因此本文的诊断结论是：可测量的是**方向条件的方差**（沿位移方向的 routine sd：代码 0.198 vs 其他域
0.056–0.107），以及**在 routine 高方差专家上的位移份额**（代码 0.626 vs 0.288–0.517）。这两个量在本
数据上分开了代码与其他域，但它们都需要一个"位移方向"，而位移方向在部署时不可知——**把它变成检测器
需要的是一个不依赖已知方向的替代物，本文没有提出也没有评价任何这样的替代物。**
