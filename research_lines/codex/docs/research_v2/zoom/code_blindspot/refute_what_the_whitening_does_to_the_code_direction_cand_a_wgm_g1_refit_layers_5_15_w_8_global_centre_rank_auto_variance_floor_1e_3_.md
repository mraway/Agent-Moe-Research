## 0. 结论（一句话）

**判定：refuted = false。** 承载该 lens 的三个核心数字我用自己的代码逐一复现，量级与小数位全部吻合；
它提出的机制在我设计的 4 项攻击（token-class 混淆、参照池混淆、白化指数反事实、逐条 n=8 脆弱性）下**没有被推翻**，
而且在一个同事没做的检验（按"最低方差十分位能量"给 8 个域排序）下**变得更强**。

但有 **3 处必须修正的表述**，其中第 1 条是因果方向错误、第 2 条是机制归因不完整：

1. **"whitening divides it away" 的因果读法是错的。** 不白化时代码的窗口级 AUC 是 **0.813 / 0.799**，
   白化后 **0.797 / 0.759**——白化只吃掉 0.016 / 0.040 的 AUC。原始尺度上代码超过 routine q99 的窗口占比
   只有 **0.049 / 0.046**，本来就没有可用信号可被"除掉"。正确说法是：
   **白化是其他 7 个域获得尾部可分性的原因（>q99 从 0.006–0.246 涨到 0.310–0.922），而它对代码什么都没给。**
2. **"最高 routine 方差坐标"这个归因不完整，且部分被 token-class 混淆。** 那些高方差坐标之所以高方差，
   有相当一部分是 routine **自己内部的 prose ↔ 工具调用/结构化两态**造成的（整体 20.2% / 20.4% 的 routine 方差是
   between-mode；decile 9 的 between 占比中位 **0.278**，decile 0 只有 **0.006**）。而代码的平均原始偏离方向
   与"routine structured 模态轴"的余弦是 **0.781 / 0.765**，**8 个域里唯一一个**（其余全在 −0.34 ~ +0.25）。
   把参照换成 token-class 匹配的 routine（只用 structured routine 窗口做参照池），代码的原始比值从
   **1.61 → 1.30 / 1.54 → 1.30**，原始 AUC 从 **0.813 → 0.711 / 0.799 → 0.710**——
   **"代码原始偏离大"这句话里约一半是 routine 自己的工具调用窗口也有的成分。**（与 legal 的对比仍成立：
   同一 structured 参照下 legal 是 0.98 / 1.01、AUC 0.497 / 0.535。）
3. **n=8 的脆弱性比 lens 写的更强一点。** "gain ≈ 1"确实 8/8 成立（且 51 条非 programming drift 里只有 1 条落进
   同一区间），但**"原始偏离大却被白化除掉"只在 5/8 条上成立**（b2-f2-014 rawR 1.04/0.99、b2-f2-015 1.16/1.09
   本来就没偏离，b2-f2-012 只有 1.44/1.37）；我的方向检验也只在 **6/8** 上成立
   （b2-f2-014 cos = −0.141/−0.191，b2-f2-015 cos = 0.416/0.407）。
   另外 **programming 域级 AUC 0.797/0.759 主要由 b2 的 3 条弱 trace 拉低**：3 条 b1 代码 trace 的 AUC 是
   0.917–0.949（高于 travel_planning 全域 0.862/0.867）。
