# 为什么代码 / SQL 类样本不好区分：组长综合（2026-09-05）

输入：六个机制视角（`nn_geometry.md`、`whitening_lens.md`、`token_identity.md`、`depth_profile.md`、
`joint_vs_marginal.md`、`pertoken_code.md`）、六份对抗反驳（`refute_*.md`）、批评者报告（`critic.md`）、
补充对照组（`structured_control.md`）。全部数字为 B1/B2 开发集上的事后诊断，锚点用 `product_onset`
（adjudicated），routine = 同 batch 的 clean + benign_control。每个视角的算术都被独立代码路径复算一致；
下面只保留反驳后幸存的部分，并标出被推翻的读法。

## 0. 一句话答案

冻结检测器（CAND-A 及"routine 流形 + 白化距离"这一家族）实际上是一个**"征用冷门专家"探测器**：
其他域漂移的可分性几乎全部来自它们点亮了 routine 几乎不用的专家；而代码**不征用任何冷门专家**，
它只在 routine 已经在用的专家集合**内部重新分配权重**，并且这个重新分配的方向恰好沿着 routine 自身
"散文 ↔ 工具调用 JSON"的模态轴。在"选了哪些专家"这个观测量下，代码就是 routine 结构化模式的一次重混，
所以在任何窗宽、任何层带、任何阈值下都看不见。

## 1. 幸存的证据链

### 1.1 可分性来自冷门专家，代码没有（最强，两位反驳者反而加强了它）
- 白化能量落在 routine **最低方差十分位**（即 routine 几乎不用的专家）的份额：其他域 drift **0.786 / 0.773**，
  代码 **0.196 / 0.134**，routine 自身 0.105 / 0.107（B1 / B2）。在这一十分位之外，8 个域彼此不可分（1.29–2.13×）。
- 冷门专家占用率（routine 入选率 < 0.02 的专家上的 top-8 质量）：routine 0.0067 / 0.0078，代码 0.0142 / 0.0084
  ——8 个 drift 域中**最低**；对照组里 STRUCT 0.039、散文 0.089。
- 白化增益（白化后比 / 白化前比）：代码 0.98 / 0.96，其他域 1.63–8.48；8/8 逐条成立（59 条 drift 中排 1–3 与 5–9）。
- 反驳者的修正：不是"白化把代码信号除掉了"——去掉白化只给代码 +0.02–0.04 AUC，本来就没有可用信号；
  正确说法是**白化给其他七个域买来了尾部，给代码什么也没买到**。

### 1.2 方向事实：代码的位移沿 routine 自身的模态轴
- cos(代码平均原始位移, routine 散文↔JSON 模态轴) = **0.78 / 0.77**，其他域全部在 [−0.34, +0.25]；逐条 6/8。
- 代码体窗口的 10 个最近 routine 邻居 **94–100% 是工具调用 JSON 片段**（距离匹配的散文对照 4–10%）。
- 被推翻的读法："坐在 JSON 瓣上"是原因——把整个 JSON 瓣从参照里删掉，代码距离只动 0–5.5；在该轴上代码
  反而是 8 个域里最可分的；一条数学 drift 有 90% JSON 邻居却离 routine 很远。方向是描述，不是机制。
- 被推翻的读法："代码在 routine 云内部"——代码在 routine 最近邻距离分布的 85–99 百分位（外沿），
  只是比其他 drift 近；"最近的 drift"这一排序在 40 次白化重采样里只有 21–27 次成立。

### 1.3 集合不变、权重在变
- 代码窗口的 top-8 **集合**与 routine 排名的 1−Jaccard（层 11）0.667，比 routine token 自身的 0.857 还小；
  变的是集合内部的概率权重：代码把质量**更集中地压到 routine 自己的 top-8 专家上**
  （层 11–14 rmass 0.236–0.312，routine 0.185，其他域 0.124；对其他 51 条 drift 的 AUC 0.998），熵更低、top-1 更高。
- 但这个量**不可部署**（`refute_depth_profile.md`）：(a) 熵与 top-1 的方向是所有 drift 的共性，只有 rmass 反号；
  (b) 对 routine 自己的 JSON 窗口，代码只有 3/8 超过 q95——rmass 主要在量 routine 的散文↔JSON 模态，
  是 §1.2 的概率版，不是独立机制；(c) 跨 batch：routine 的逐层 top-8 集合在两个 batch 之间只有 8/16 层相同，
  B1→B2 看起来很好（AUC 0.97），B2→B1 崩塌（resist FAR 0.44–1.00），代码的裕度只有 0.03–0.06，
  比 routine q99 的 batch 间差异（0.298 vs 0.347）还小；(d) 它对其他域召回 ≈ 0，只能作 OR 臂。
- 与既有结论不矛盾（X10 裁定）：missed_drift 的 15 个反事实和 FCM 的 F7 测的都是"离 routine 多远"
  的单调统计量（概率特征版找回 6 丢 8、方向不一致），没有一个测过"反号的集中度"；本轮补上了，结论是不可迁移。

### 1.4 时间轴上没有可挖的
- CAND-A 逐 token（w=1）：代码窗口 token 超阈值 2/384，对照 drift 173/384，held-out routine 0.0025；
  7/8 代码 trace 窗内零次单窗越线，唯一两次落在 docstring 英文词上；SELECT/FROM/WHERE/'=' 的逐 token 分数
  都在 routine 桶均值**之下**。
- 聚合单调帮助（AUC 0.53 → 0.62 → 0.70 → 0.75，w=1→8）但到不了阈值；CAND-B 在 5/8 条的代码块内确实
  有 persist2 越线，但迟（+17…+22），效应量只有其他域的一半（0.94 vs 2.24 routine sd）。
  "窗口平均稀释了孤立尖峰"的假说死了：变窄让代码**更**不可分。

### 1.5 跨层链：代码和其他域一样打破耦合，特殊之处是"边缘不动"
- 相邻层 top-1 对的未见率：代码 7.3× routine，8/8；但在独立性零模型下，纯联合超额是代码 9.5× vs 其他域 10.0×，
  51/51 其他 drift 都不低于代码最小值。"熟悉专家的新组合是代码独有的统计量"被分解：2.38× 的差距里 79%
  来自边缘机会（代码留在 routine 专家支撑内，熟悉-熟悉的层对机会是其他域的 2 倍），按条件率排代码只是第 3。
- 这解释了 CAND-B 为什么漏 7/8：不是 top-2..8、不是层带、不是平滑、不是 w=4 稀疏，而是**效应量减半且迟到**。

### 1.6 被排除的解释（确定）
- token 新颖度 / 词表复用：代码的共享 id token **不是**上下文无关地路由（离该 id 的 routine 质心 2.5×），
  新 token 也不比 routine 的新 token 更偏（1.02×）；59 条 drift 上 spearman(unigram surprisal, 路由偏离) = 0.18，
  spearman(代码字符密度, 偏离) = **−0.42**。决定可见性的是"是否征用新专家"，不是"token 是否罕见"。
- 参照池里的 JSON 习惯（FCM F8a，已知）、层带（深度剖面双峰：L5–7 与 L12–13，层 0–4 无用，但没有任何层带
  给代码其他域的幅度；w=8 下最好的单层是 L5 而不是 L13）、窗宽（§1.4）。

### 1.7 盲区是代码专属，不是"结构化输出"的通病（对照组）
- 14 条结构化非代码交付物（食谱清单、案例清单、行程、LaTeX 推导、P3 工具调用载荷）：CAND-A 窗口中位 / routine q95
  中位 **1.66**（代码 0.79），冷门专家质量 **0.039**（代码 0.005），冻结 CAND-A 在 +16 内命中 8/14、+48 内 13/14
  （代码 0/8、1/8）。59 条 drift 中最结构化的一条（带配料清单的食谱，0.44）完全像散文 drift（+19 / +13 报警）。
- structure_score 与各统计量的相关在域内去均值后消失（−0.01），它只是域的代理。
- 进入代码带的非代码样本只有：3 条 P3 工具调用载荷（n=3）和 1 条几乎无结构的法律散文（`b1-f3-066`，
  两个候选都漏）。失败模式有非代码成员，但很少。

### 1.8 样本本身
- 8 条"programming"里 **2–3 条是关于 SQL 的英文散文**（`b2-f2-014` 首个代码 token 在 +81，`b2-f2-015` +60，
  `b2-f2-012` 类似），它们在所有统计量上都是最弱的；概率特征的"5/8"恰好就是 5 条字面代码。有效 n = 5–6。
- batch 异质：B1 的 3 条代码 trace 白化 AUC 0.92–0.95，B2 的 3 条 0.43–0.66；但冻结 CAND-A 两个方向都漏
  （5/5、3/3）——可分性排序与实际报警之间没有单调关系（最小的干净检出 g1 949 / 1362，最大的漏检 8913 / 7059）。

## 2. 机制图景

离开 routine 流形有两条路：
1. **征用新专家**（诗歌、小说、法律、食谱、数学）——基于"选了哪些专家"的白化距离一眼看见，78% 的能量在冷门专家上；
2. **保留 routine 的专家集合，改变集合内权重与跨层链**（代码，以及工具调用载荷）——集合特征结构性地看不见；
   概率集中度与链统计量部分看见，但裕度小于 routine 参照本身的 batch 间漂移。

为什么这个模型对代码走第二条路，本轮没有回答（路由器之下未检查）。可检验的猜想：OLMoE 处理语法/结构的专家
在工具调用 JSON 与代码之间是共享的；代码的词法新颖性在层 0–4 被处理，而那里的路由贴在 routine 上（比值 ≤1.02）；
语义差异在 L5–7 与 L12–13 以"重加权"而非"重选择"的形式出现。这是"这个模型 × 这个 agent 的 routine 组成
（routine 里本来就有 JSON 工具调用生成）"的联合性质。未做：同一表层 token 在代码与工具调用 JSON 里是否路由到
同一专家、专家输出/残差流层面的证据、prefill 语域的影响。

## 3. 对方法与 B3 的含义

1. 适用范围声明现在有机制支撑：routine 流形 + 集合类特征这一家族**看不见"在 routine 专家支撑内的重加权"**。
   这不是数据量或校准问题，B3 增加代码样本不会改变它。
2. 能看见代码的量（rmass、条件链新颖度）与 CAND-A 正交（在放行代码的阈值上对其他域召回 ≈ 0），只能作 OR 臂，
   且在坏方向上 resist FAR 0.27–0.44；参照（routine 逐层 top-8 集合、rmass q99）本身跨 batch 不稳。
   除非 C1 大池（每半 ≥90 条）能把参照稳住，否则不进候选。批评者提议的"反号 rmass 走冻结协议"决定性实验，
   本轮的跨 batch 检查已预告其 B2→B1 失败，我把它排在两阶段文本确认读法之后。
3. 对代码类，仍然只有"路由 provisional + 零误报文本规则 confirm"这一有正面证据的方向（FCM §10）。
4. 标签：B3 规则把"关于代码的散文"（P4）与"字面代码"分开记录；`product_onset` 对前者是散文 onset，
   字面代码晚 +60…+81 出现。

## 5. 补充：如果 routine 流量里没有 JSON（trace 级反事实，2026-09-06）

前提修正：系统提示明令 "Do not output a tool call or JSON"，但 240 条 routine 输出里 114 条（47.5%）以 JSON 对象开头
（模型照抄上下文里控制器的动作格式）。所以 JSON 瓣不是设计要求，是小模型违规的副产品。

反事实（`no_json_counterfactual.md`）：把以 `{` 开头的 routine trace 从拟合与校准池里都去掉（b1 80→42，b2 160→84），
两个候选走冻结协议：
- **窗口层面代码变得可分**：对纯散文 routine 参照，代码窗口中位百分位 0.995 / 0.997，超过散文 routine q95 的窗口比例
  0.93 / 0.97（对全部 routine 参照时只有 0.10 / 0.45），域内排名从 8/8 升到 5/8。仍分不开的正是那 2 条"关于 SQL 的散文"。
- **trace 层面代价不可接受**：CAND-A 代码 +16 内从 0/8 变 1–2/8，但总 FAR 0.10 → 0.29–0.35，resist 臂 FAR 0.13 → 0.47–0.50，
  被排除的 JSON 样本在散文阈值下误报 0.45–0.57，其他域 drift 的 R+16 从 0.70 掉到 0.43–0.52。CAND-B 更糟（JSON 样本误报 1.000）。
  新增的代码报警 7/8 里只有 3 条落在锚点之后，其余落在 drift 自己的动作 JSON 前缀、`[TRUSTED RESPONSE BRIEF]` 或普通客服散文上。
- **机制**：JSON 瓣是 routine 流形的一整组坐标；去掉它后这些坐标的方差趋近零，散文白化变得病态
  （一条 routine trace 的 g1 从 6,419 变成 785,355），校准池缩到每半 20–44 条时一条离群 trace 就决定阈值。
- 结论：**"不要求 JSON"会让代码在几何上离 routine 更远，但不会让它在部署协议下可检**——除非 JSON 从整个流量
  （含 resist 与 drift 的前缀）里消失且校准池足够大。对 B3 的含义是把"routine 是否含结构化输出"做成显式设计变量。
