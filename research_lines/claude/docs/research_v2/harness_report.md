## 2. 规范留白处的实现决定（全部可配置，默认值写在下表）

| 编号 | 项 | 决定 | 理由 |
|---|---|---|---|
| D1 | 报警比较符 | 默认 `>=`（`comparison="ge"`），可切 `gt` | §1.6 要求显式选择；`>=` 与组长 pilot 一致。P1–P3 用 `>`，验收 (a) 用 `gt` |
| D2 | 模式 D 的合并规则 | 默认 `disjoint`：target scenario 按 pair_group 排序后奇偶对半；以第 h 半做校准时，**只评价另一半的 trace**，两半合起来每条 target trace 恰好被评价一次，且其校准池与它的 scenario 严格不相交（§1.6 的字面要求）。`pooling="pilot"` 复现组长 pilot：attack 臂（drift + resist）在两个半上都被评价、计数除 2 | pilot 的规则让 drift/resist 与自己 scenario 的 clean/benign 同处校准池，违反“scenario 不相交”；但需要它来复现 pilot 数字 |
| D3 | 位置桶 | `b = end // 32`；从最高桶向下合并，直到尾桶的**贡献 trace 数** ≥ 30（`min_bucket_traces`）。非尾桶若 trace 数不足则沿用下一低桶的 μ/σ。可选 `bucket_cap`、`bucket_min_criterion=windows` 复现 pilot（cap 3、按窗口数计） | §1.6 写的是“合并到 ≥ 30 条 trace”；pilot 实际是 cap 3 且按窗口数计。两者在 B2→B1（每半只有 40 条校准 trace）差别明显，见 §4 |
| D4 | 模式 T | μ/σ 用**全部**源侧 routine 拟合并用于给 target 打分；阈值 h 用 scenario 对半交叉拟合的 out-of-fit 最大值（每半用另一半的 μ/σ 标准化）合并后取次序统计量 | §1.6 只说“对半交叉拟合得到 out-of-fit 最大值”，未说打分用哪套 μ/σ |
| D5 | `runlen(m,c)` 的阈值 | §1.5 把 runlen 定义为“连续 m 个窗口 z ≥ c”，c 是常数。因此 runlen 的统计量取“最近 m 个窗口的最小 z”，阈值**固定为 c**，不做 conformal。其 FAR 不受 α 控制，按实测报告 | 字面遵守 §1.5；后果见 §5.4 |
| D6 | 窗口特征尺度 | `selection_rate_windows` 返回 counts/width（每专家在窗口内的入选率 ∈ [0,1]），即 pilot 的尺度；白化后与 `selection_window_signatures` 的 counts/(width·k) 只差方差下限 1e-3 的相对大小 | 复现 pilot 需要同尺度 |
| D7 | 边界前审计的窗口文本 | `trace.json` 的 `model_generation` 事件只有 `output_token_ids`，**没有** `output_token_texts`；文本用本地 OLMoE `tokenizer.json`（离线）逐 token 解码重建 | 规范假定有 token_texts，实际没有 |
| D8 | 严格 pre-onset FAR 的分母 | 主表用“存在 `end < onset` 窗口的 drift 条数”（pilot 口径），同时输出 `pre_alarm_rate_all_drift`（分母 = 全部 drift，P1–P3 口径） | 两个口径都在文献里出现过，并列避免歧义 |
| D9 | 经验尾部 rarity | 默认路径完全不做（§1.6 要求） | — |
| D10 | scenario bootstrap | 以 pair_group 为重抽样单位，默认 500 抽、只对 `mode=D` 与读法 `max`/`persist2` 计算（成本） | 全部候选做 bootstrap 会把单次运行拖到分钟级 |

### 4.2 差异归因（消融，均为 w=16 / cb / D / α=0.10 / max）

| 运行 | 合并规则 | 位置桶规则 | B1→B2 FAR_all | B2→B1 FAR_all |

`g1_acceptance_pilotrule` 与 pilot **逐单元完全一致**（B1→B2：FARall 0.120 / FARc 0.113 / FARb 0.087 /
FARr 0.189 / pre 0.120 / R4 0.086 / R8 0.229 / R16 0.629 / RF 0.800 / lat 13 / reach8 0.886；
B2→B1：0.099 / 0.075 / 0.125 / 0.094 / 0.206 / 0.083 / 0.292 / 0.625 / 0.771 / lat 10 / reach8 0.833；

13.5 vs 14，来自 pilot 把 attack 臂计两次后中位数的并列取法）。

结论：3.5 条的差异**完全由两条被文档化的规则差异产生**，其中主项是位置桶规则（D3）：B2→B1 方向的部署侧
校准池每半只有 40 条 routine trace，按“尾桶 ≥ 30 条 trace”合并会把桶上限压到 1–2（B1 方向可到 2–3），
标准化因此更粗；pilot 的“cap 3、≥30 窗口”保留了 4 个桶。合并规则（D2）贡献约 1.5 条。
两条规则都可通过 `--bucket-cap 3 --bucket-min-criterion windows --pooling pilot` 复现 pilot。
harness 的默认仍取规范字面（§1.6 的“≥30 条 trace”与“scenario 不相交”）。

**这条差异本身是给三个方案作者的警告**：B2→B1 方向的部署侧校准样本量（每半 40 条）低于 §1.6 要求的
≥100 条；§1.6 允许把 B1 `brief=present` 的 120 条并入校准池（`--b1-present-calibration`，harness 已实现，
默认关闭，见 §9 限制 3）。

## 5. 验收 (c)：基线表（S1 两方向，供三个方案 scorer 直接对照）

所有表的列：`FARall` = non-drift trace FAR（clean+benign+resist）；`FARc/FARb/FARr` = 三臂分层 FAR；
`preS` = 严格 pre-onset FAR（分母 = 有 pre-onset 窗口的 drift）；`preTol` = 容差版（报警 `end < onset−8`）；
`R4/R8/R16/RF` = onset +4/+8/+16/final 的 clean recall（clean = 无严格 pre-onset 报警）；
`R16t/RFt` = 8-token 容差带下的同一指标；`lat` = 命中 trace 的中位 latency；
`cb+16` = 相对 completion boundary 的 +16 recall（连续性指标）；`on/1k` = 每 1,000 个 negative position 的
alarm onset 数。分母：B1→B2 的 non-drift 205 条（clean 80 / benign 80 / resist 45）、drift 35；
B2→B1 的 non-drift 96 条（40 / 40 / 16）、drift 24。

`S0*` 是**有监督参考**（difference-of-means 方向用了 drift 标签），不是检测器，只用来说明监督买到了什么。
`T1(PCA32)` 是规范字面的 T1；`T1(full)` 是同一分数不做 PCA 投影的版本，理由见 §5.3。

### 5.3 T1 的 PCA-32 崩塌（一个必须报告的失败）

§1.9 规定 T1 = 窗口静态 embedding 均值在 routine 上的 kNN-10 新颖度、PCA-32 空间。按字面实现后，
drift 后窗口的分数**低于** routine：trace-max AUROC（drift-post vs routine）为 0.214（B1→B2）与
0.169（B2→B1），即排序反了；报警层面 `RF` 0.029 / 0.000。

诊断（w=8，B1→B2，routine=cb 的 8,647 个 routine 窗口）：

| 空间 | 是否先按维标准化 | drift-post vs routine AUROC |
|---|---|---|
| PCA-32 | 否 | 0.214 |
| PCA-128 | 否 | 0.268 |
| 全 2,048 维 | 否 | **0.930** |
| PCA-32 | 是 | 0.135 |
| PCA-128 | 是 | 0.147 |
| 全 2,048 维 | 是 | 0.900 |

机制：域外文本的 embedding 新颖度主要落在 routine 主成分的**正交补**上；投到 routine 的前 32/128 个主
成分后，drift 窗口反而更靠近 routine 云的中心，kNN 距离变小。这与 §2 的 E19（单类对秩敏感）是同一类
现象，但方向相反（这里是低秩投影直接把信号丢掉，而不是高秩带来误报）。

因此本报告并列 `T1(PCA32)`（规范字面）与 `T1(full)`（`{"components": null}`，不做投影）。**给 scorer
作者的建议：与 T1 比较时用 `T1(full)` 行**；`T1(PCA32)` 只作为"低秩投影会杀死文本新颖度"的反例保留。

## 8. 给 scorer 作者的 API

### 8.1 接口（§1.10）

```python
class MyScorer:
    window_width: int                 # 因果窗口宽度 w（逐 token 方法写 1）
    requires_positives = False        # True 只用于有监督参考，harness 会给整个拟合侧并标记 reference_only

    def fit(self, routine_traces: Sequence[LoadedTrace]) -> State:
        """只接收 routine trace（由 harness 按 routine 定义筛好），绝不接收 drift 或测试侧 trace。"""

    def score(self, state: State, trace: LoadedTrace) -> tuple[torch.Tensor, torch.Tensor]:
        """返回 (scores[nwin], ends[nwin])。ends[i] 是第 i 个窗口的最后一个 decode token 下标，
        窗口覆盖 [ends[i]-w+1, ends[i]]；scores[i] 只能依赖 decode token <= ends[i]。"""

    def config(self) -> dict:         # 可选，写进结果 JSON
        ...
```

`LoadedTrace` 提供：`top_k_ids [16,T,8]`、`token_ids [T]`、`probabilities() -> [16,T,64]`（按需读缓存）、
`trace_id / batch / pair_group_id / fold / arm / workflow / workflow_family / channel / scenario_domain /
positive / evidence_onset / completion_boundary / token_count / group_id`。
**推理时不得使用** `positive`、`evidence_onset`、`completion_boundary`、`scenario_domain`、`channel`（§1.2）；
`workflow` / `workflow_family` 可用。

### 8.2 最小示例：`src/research_v2/scorers/my_idea.py`

```python
from __future__ import annotations

from typing import Any, Sequence

import torch

from research_v2.features import MIDDLE_LAYERS, selection_rate_windows
from research_v2.scorers import register


class MyScorer:
    requires_positives = False

    def __init__(self, window_width: int = 8, layers: Sequence[int] = MIDDLE_LAYERS) -> None:
        self.window_width = int(window_width)
        self.layers = tuple(layers)

    def config(self) -> dict[str, Any]:
        return {"window_width": self.window_width, "layers": list(self.layers)}

    def fit(self, routine_traces):
        blocks = []
        for trace in routine_traces:
            _, windows = selection_rate_windows(trace.top_k_ids, self.window_width, self.layers)
            if windows.shape[0]:
                blocks.append(windows)
        matrix = torch.cat(blocks)
        return {"mu": matrix.mean(0), "sd": matrix.std(0) + 1e-3}

    def score(self, state, trace):
        ends, windows = selection_rate_windows(trace.top_k_ids, self.window_width, self.layers)
        if not ends.numel():
            return torch.empty(0), ends
        z = (windows - state["mu"]) / state["sd"]
        return z.abs().amax(dim=1), ends          # 任意因果分数


@register("my_idea")
def _build(config: dict[str, Any]) -> MyScorer:
    return MyScorer(**config)
```

## 9. 已知限制（scorer 作者与组长必须知道）

1. **B2→B1 方向的部署侧校准样本量不足。** target B1 只有 80 条 cb routine trace，对半后每半 40 条，
   低于 §1.6 的 ≥100 条。后果：位置桶合并到 cap 1–2（见 §4.2），conformal 在 n=40、α=0.10 时取第 37 小，
   运行点抖动大。§5.9 的 bootstrap 区间宽 ±0.2。
2. **B1 `brief=present` 的额外校准池已实现但默认关闭。** `io.load_b1_present()` 会把这 120 条 trace 的
   decode 路由从原始 shard 抽出并缓存到 `artifacts/agent_v2/research_v2/_extra_routing_cache/`
   （不写入 `normal_manifold_cache`）。本轮**未**用它跑主表：首次抽取需要重读 B1 的路由 shard，
   且它们的 pair_group 与 `brief=absent` 完全不相交（40 个独立 scenario），并入后半池 n=100。
   建议由方案作者按 §1.6 主表要求打开 `--b1-present-calibration` 并同时报告不打开的敏感性。
3. **P0（prefill route propensity 常数参考）未实现。** 冻结的 routing cache 只含 decode 路由；prefill
   路由需要另建缓存（重读全部 360 条 trace 的 prefill shard）。§7.1 允许 S0/P0 可选，本轮做了 S0、跳过 P0。
4. **B0（v1 配方在本协议下重训）未实现**（§1.9 列为有监督参考，§7.1 的验收未要求）。
5. **`runlen` 的三个配置 FAR 不受控**（§5.4），只有 (8,2) 可用作运行点。
6. **T1 的规范字面版本（PCA-32）在本数据上排序反向**（§5.3）；请用 `T1(full)` 作对照行。
7. **S2/S3 的模式 D 阈值极保守**（校准 n=10–12），其 FAR 与 S1 不可直接比较；S3 的域间比较建议用
   模式 T 或同时看两种模式。
8. **Q1 面板的 z 用全部 target routine 拟合**（不做半分），与报警用的 z 不是同一套统计量；它只用于诊断。
9. **审计的 `classification` 列是空的**：harness 只生产证据，分类由人或组长完成。
10. **bootstrap 默认只对 `mode=D` 与 `max`/`persist2` 计算**（`bootstrap_readings` / `bootstrap_modes` 可改）。
11. `result.json` 因为存了每条 trace 的分数序列而较大（G1 的 S1 全网格约 19 MB）；不需要时加 `--no-streams`。
