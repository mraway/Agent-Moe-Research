## 2. 口径：为什么必须重算，以及用哪条代码路径

**H 的单位是 look，不是 token。** `detector_harness_g.md` §5（D6）已经写死：
序贯保证是关于"看了多少次"的；G 上视图会丢通道、因果窗口在通道边界重启，
所以 look 与 token 不成仿射关系。`trm3_g.h_horizon(lengths, min_survivors=90)` 收到的 `lengths`
是每条校准 episode 在该 (视图, w) 下的**端点数**，返回 `H = 降序第 90 个端点数`。

**一个 look = `trm3_g.segmented_windows` 的一个端点**：先用 `io_g.channel_runs` 把 episode 切成
极大同通道连续段，段长 < w 的段不产生端点，段内做步长 1 的因果窗口。
于是 V1 / `message` / w=8 的端点数 ≈ 0.90 × token 数（**不是** token/8）。

**为什么不用 `run_detectors_g.py --normal-only-smoke`。** 该开关是**数据纪律**开关（只允许正常臂），
不是"只算存活"的开关：CLI 的每一次调用都会走 `trm3_g.calibrate_g`，那会拟合统计量、做通道条件化标准化、
产出参照集、p 值、报警与 FAR。任务明确要求不产生检测分数，所以本轮改用
`scripts/research_v4/h_rule_g.py`，它直接调用 loader 与 `trm3_g` 的**同一批**函数：

* `io_g.load_g(..., variants=NORMAL_VARIANTS, tag_scope=..., cache_dir=None)` —— 与冒烟同一个 loader、同一套通道标记；
* `trm3_g.segmented_windows(features, episode.channel_tags, view, width)` —— **同一个函数**给出端点网格，
  但传入的 `features` 是一列 0（`[T, 1]` 零张量）：`ends` 只依赖 tag、视图与 w，
  所以拿到的端点与检测器会看到的**逐位相同**，而没有任何路由数值进入计算；
* `trm3_g.h_horizon(lengths, min_survivors=90)` —— **`calibrate_g` 内部调用的就是这一行**
  （`trm3_g.py`：`horizon = h_horizon([len(z) for z in z_streams], min_survivors=min_survivors)`，
  `len(z)` 就是端点数），所以本文的 H 与检测器届时自己算出来的 H 是同一个函数的同一个输入。
* `cache_dir=None`：本轮不向 `g_routing_cache/` 写任何东西。

E+16 可达性代理**不可计算**并已跳过：正常池 600 / 600 条 `trajectory_class = silent`、E 事件 0 条，
没有锚点就没有 `anchor + 16` 可言（`view_anchors` 会返回 `reason = unlabelled`/无正例）。

## 6. 与 token 计数代理（384 / 93 存活）的差异

标注报告 §4.3 用**token 计数代理**（`generated_token_count ≥ k`）给出
"H = 384 token（w=8 的 look 48），过滤后 G-cal 存活 93，余量 3"。本轮的 look 口径给出
**H = 352 look，存活 90，第 H 个 look 落在 token 379 – 393**。差异有三层，逐层说清：

### 6.1 token 轴本身完全对上（代理没有算错 token）

本轮用 loader 的 `top_k_ids.shape[1]`（拼接后的生成 token 数）重算 token 轴存活，
与包字段 `episode.generated_token_count` 得到的报告数字**逐条相同**（见**表 H**）：
过滤后 G-cal 原始 token 口径 H = **386**、k = 384 存活 **93**；
过滤后 G-fit 401 / 102；未过滤 G-cal 397 / 99；未过滤 G-fit 407 / 109。
四个数与 `g_normal_annotation_report.md` §4.3、`g_fitcal_run_log.md` §9.3 一字不差。
**所以差异不是数据分歧，是口径分歧。**

### 6.2 代理把 look 数当成了 `token // w`，而 harness 的窗口是步长 1 的

报告的"整 look"换算是 `H_token // w`（384 // 8 = look 48），即**假设窗口不重叠**。
harness 的 `segmented_windows` 用的是**步长 1 的因果窗口**（`features.window_means`：
`ends = arange(w-1, T)`），一条长 T 的通道段产生 `T − w + 1` 个端点。
于是本池 V1 / message / w=8 的 look 数 ≈ **0.90 × token 数**，而不是 token/8——
"look 48"与"look 352"差了 7.3 倍，两者根本不是同一把尺子。
**代理的 look 号不可直接写进冻结**：`--h-min-survivors` 的单位是 harness 的 look，
如果把 48 写进去，检测器会在每条 episode 的第 48 个端点（≈ 第 55 个 token）就删失，
相当于把视界压到设计意图的 1/7。

### 6.3 即使换算成 look，"384 token"与"352 look"也不是同一个集合

look 数 = token 数 − Σ(每个通道段丢的 w−1) − (短于 w 的段整段丢掉的 token)。
本池这个缺口逐条是 **27 / 28 / 42**（2 步 4 段 / 3 步 6 段，§3）。
所以"活到 352 个 look"要求 token ≥ 380（2 步）或 ≥ 394（3 步）——
**门槛依 episode 的步数而变**，这正是 D6 说的非仿射。具体后果：

* `{look ≥ 352}` 的 90 条是 `{token ≥ 384}` 的 93 条的**真子集**：
  交集 90、只在 token 侧的 **3** 条、只在 look 侧的 **0** 条。
* 那 3 条是 3 步 episode（缺口 42），token 数够 384 但端点不到 352。
* 因此 look 口径比 token 代理**更严**（少 3 条存活），而不是更松；H 的数值大（352 > 48）只是尺子不同。

### 6.4 结论

代理在**它自己的轴上**是对的，也正确地完成了它的任务（确认过滤没有集中淘汰长尾）；
但它给出的数字 **384 / look 48 / 存活 93 / 余量 3** 都不能直接写进冻结。
可以写进冻结的是本文的 look 口径：**主格 H = 352 look，存活 90，第 H 个 look 在 token 379–393**。
两者的桥是"token ≈ look + 28（2 步）/ + 42（3 步）"，中位对应 token **379**——
与代理的 384 只差 5 个 token，**代理对"H 大致落在 380 token 附近"这件事的判断是对的**。

## 9. 开放项

1. **H 是 12 个格各一个值，不是一个标量。** 预注册必须写清"主格 = V1 / message / w=8 / H = 352"，
   并把另外 11 个值一起写死；跨格比较召回时两侧看的 look 数不同，这一点要在结果表里注明。
2. **`tag_scope` 仍未冻结**（`detector_harness_g.md` §11 开放项 10 / §12.6）。它把主视图的 H 从 352 压到 314（−11%），
   删失端点从 11.5% 抬到 13.8%。本文给出两套完整读数，但**选哪一套仍需组长裁定**。
3. **H 的数值对"第 90 名"这一条路径敏感，但门不敏感。** 剔掉最长的 1/2/3/5/10 条，H 只掉到 351/348/348/345/340；
   而 `H ≥ 128` 这道门要被打破需要过滤后 G-cal 少掉 **151 条**长于 128 look 的路径。
   标注报告 §7 第 2 条的"余量 3"是 token 代理口径的产物，在 look 口径下不成立（§6）。
4. **删失掉了三分之一的校准路径的尾巴**（路径 31.9%、端点 11.5%）。这是 H 规则的代价，不是错误；
   但它意味着"H 之后发生的攻击"在设计上就不可检测，评价时 X 常落在 H 外这一点（设计 §15.1）要在数据卡里重申。
5. **两臂的长度不完全对称**：过滤后 G-cal 的 benign_control 中位 346 token / 304.5 look，
   clean 328 token / 286 look；H 处的 90 条存活里 benign 49 / clean 41。
   这不影响 H（H 只看混合池），但**匹配 FAR 与长度三分位的臂内平衡应在下一轮检查**。
6. **`E+16` 可达代理无法在正常池上计算**（0 条 E 事件），所以"+16 视界是否落在 H 内"这条设计断言
   仍然只能在攻击臂标注回来后验证。
7. **本轮没有验证 `calibrate_g` 端到端复现这些 H**（那会产生检测分数，超出授权）。
   两者共用 `h_horizon` 且输入定义相同（`len(z)` = 端点数），但**第一次真正的端到端复核应在
   检测器首跑时做一次断言**：`result.json` 的 `calibration.horizon.H` 必须等于本文表 D 的对应值。
8. **并发改动提示**：本轮进行时另一路 agent 正在修改 `src/agent_v3/packets/{build,schema}.py`
   与 `scripts/research_v4/packets_build.py`（包**构建**路径）。解盲用的是 `packets/validate.py`（未被改动）
   与 `build.read_jsonl`（未被改动），且重跑逐字节可复现；但若那一路后续重建了 packet，
   `final_unblinded.jsonl` 需要按新的 packet 哈希重新生成一次。
