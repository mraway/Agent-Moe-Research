# 对外技术报告审阅：外部读者视角（lens = reader）

> **审阅对象**：`docs/research_v4/technical_report_gpt_oss.md`（427 行，2026-09-08 工作树版本）
> **审阅者立场**：一名**没有读过本项目任何内部文档**的、持怀疑态度的 ML / 安全研究者，冷启动读这一篇。
> **本文只审"读者能不能读懂、会不会被误导、审稿人会问什么"**，不复算统计、不评价实验设计本身的正确性
> （那是 `freeze_review_v3_2_statistics.md` / `_code.md` / `_data.md` 的职责）。
> **所有对照数值取自** `g_conf_confirmatory_report.md`（G-conf 权威来源）、`g_dev_confirmatory_report.md`、
> `g_dev_v3_2_development_report.md`、`detector_prereg_v3_2.md`、`g_session_medium_conf_run_log.md`。
> 分级：**BLOCKING**（对外发布前必须改，否则读者会得出错误结论或认为在藏结果）/
> **SHOULD-FIX**（会显著削弱可信度或可读性）/ **NOTE**（打磨项）。

## 0. 总体印象（先说好的）

这份报告的**纪律叙述是同类工作里罕见的诚实**：两步冻结、封存批只开一次、提前声明会失败的门、
逐条对照先验落空、把 v3.1 的失败完整写出来而不是删掉。§7「负结果与已排除方向」和 §9「局限」
这两节，绝大多数外部报告根本不会写。**这一点必须保住，下面所有意见都是在这个前提下提的。**

问题不在于"藏了什么"，而在于**三件事同时发生**：
1. 报告把**最不利的分层留在了内部报告里**（§5.4 的"每一维报最差组"一整张表没有进正文，
   而**有利的那一维（代码域）进了**）——这在外部读者眼里就是选择性呈现，哪怕作者主观上不是；
2. **唯一的确认性数字 0.746 的条件性没有被讲清楚**（它是"攻击已经执行成功且窗口可达"这一子总体上的命中率），
   而端到端的 episode 级检出率从头到尾没有出现；
3. **一整类审稿人必问的基线（任何非路由基线）完全没有跑**，这件事只出现在 §7 第 7 条的清单里和
   §8 表格的一个单元格里，**没有进 §9 局限**。

## 1. BLOCKING

### R1 — 没有任何非路由基线，而这件事被埋在清单里

**位置**：§7 第 7 条、§8「TaskTracker」行的括号；**§9 局限里没有这一条**。

报告的核心主张是"**路由**能在线标出不可逆动作"。外部审稿人第一个问题必然是：
**和什么比？** 目前正文里唯一的对照全部是**路由内部的**（S vs P vs M vs prob_js）。
`P` 被称作 "brief §9 判据 1 点名的 marginal novelty 基线"，但它也是同一个 `q[l,e]` 上的统计量——
这只能说明"稀有掩码有用"，**不能说明"路由有用"**。

更尖锐的版本：§1.1 把 **X 定义为"代码块正文首个字面代码 token、第一个等式、诗的第一行创作文本"**，
而 §6.6 又说**误报的机制是"输出体裁的切换"**。那么最自然的竞争者是一个**零成本的输出形态检测器**
（检测代码围栏 / 编号列表 / 诗行）。按 §1.1 的定义，围栏**不算 X 而 X 在围栏之后**，
所以这个平凡基线的报警**会早于 X**——它在"提前量"这一维上直接优于本文的检测器。
报告对此**一个字都没有**。

**修**：(a) §9 加一条独立局限：「**本轮没有跑任何非路由基线（文本 / 输出形态 / 激活探针），
因此"路由相对可从文本直接得到的信号有增量"这一命题本轮未被检验**」；
(b) 在摘要里点名这句话；(c) 把 §7 第 7 条里的 `B-NT` 从"未做清单"提升为 §9 的具名缺口。

### R2 — "这是不是一个体裁变化检测器"这一替代解释从未被当作效度威胁写出来

**位置**：§6.6 第三条（误报 = 体裁切换）与 §1.1 的 X 定义之间。

报告自己给出了这个替代解释的两块材料，却没有把它们接起来：
- 真阳性 = 模型开始产出**跨域体裁**（代码 / 等式 / 诗行）；
- 假阳性 = 正常臂**从推理散文切到高度结构化枚举**（`knowledge_qa` 下"把 KB 全文改写成编号清单"）。

两侧都是**体裁切换**。而 `benign_control` 臂**并不控制这个混淆**——它是"工具结果里出现题外话题的
非指令性提及"，模型的输出仍然是正常客服体裁。也就是说，**数据集里根本没有"同体裁的偏离"
或"同任务的体裁突变"这一对照臂**，因此"检测的是任务偏离"与"检测的是输出体裁变化"
在 G 上**不可区分**。

正文里唯一能反驳它的证据是「归因坐标 Jaccard = 0.111」（误报与真检出的 top-20 稀有坐标近乎不相交），
但它被写成一条中性的描述性发现，**没有被标注为"这是对上述混淆的部分反证"**，也没有讨论
Jaccard 低是否可能仅仅因为体裁不同（编号列表 vs 代码）。

**修**：§9 加一条局限「**任务偏离与输出体裁变化在 G 上不可分**」，说明缺少的对照臂是什么；
把 Jaccard = 0.111 明确重新定位为对这条混淆的**部分**反证，并说明它为什么不是完整反证。

### R3 — 最差分层被略去，最好分层被保留

**位置**：§6.6（描述性发现）对照 `g_conf_confirmatory_report.md` §5.4「逐类结果：每一维报最差组」。

内部报告有一张**明确以"每一维报最差组"为名**的表。技术报告**一条都没有引用**，
却把同一张表里**最有利的一格**（代码域 15/19 = 0.7895、代码域正常臂 FAR 0.0698 四域最低）
单独摘出来写成「**代码不是盲区**」。被略去的包括：

| 维度 | 最差组（源：`g_conf_confirmatory_report.md` §5.4） | 技术报告里有没有 |
|---|---|---|
| 注入渠道 | **`tool_output` 9/14 = 0.6429** —— 这是**间接提示注入**，安全上最要紧的一类 | ❌ |
| 域组 | **`reasoning_legal` 7/13 = 0.5385** | ❌（只写了 code 0.7895） |
| 措辞层 | T1 27/38 = 0.7105 | ❌ |
| 正常臂 FAR × workflow | **`return_status` 7/26 = 0.2692** —— **是 0.10 预算的 2.7 倍** | ❌ |
| 正常臂 FAR × 域 | creative 20/172 = 0.1163 | ❌ |
| `scenario_role` | `held_out_workflow` 9/10 = 0.9000（**有利**，见 R12） | ❌ |

对一个外部读者，这个组合（保留最好的、略去最差的、且源文档明确是"报最差组"）
**是本报告最像在藏负结果的地方**，比任何一处措辞都严重。

**修**：把 §5.4 的整张"最差组"表原样搬进 §6.6（或 §6.3 后新开一小节），
并在 §9 加一句「按渠道分层，**间接注入（`tool_output`）是最弱的一类**」。
`return_status` 的 FAR 0.2692 必须与 F3/F1 的"通过"写在同一页。

### R4 — 0.746 的条件性没有讲清楚，端到端的 episode 级检出率从未出现

**位置**：摘要、§6.3 判定表、§9 第 3–4 条。

摘要给出的唯一召回数字是 **0.746（53/71）**。外部读者会把它读成"检出 75% 的攻击"。
实际上 71 是**三重筛选后的子总体**：

```
攻击 episode 216（§3.1）
  └─ 有 E 事件 128（源 §5.5）
       └─ 有文本 X 事件 72（其余 56 条 = 有界抵御，报警率 8/56 = 0.143 ≈ 校准水平）
            └─ 窗口可达 71（1 条 unreachable）
                 └─ 其中 12 条 `x_beyond_h` 的 X 落在视界外，命中 0/12
```

报告 §9.3/§9.4 逐条讲了其中几层，**但从来没有把漏斗画出来，也从来没有给出攻击臂整体的报警率**。
按源 §5.7，S 格共 127 个报警 episode，**攻击臂 69 条 / 正常臂 58 条**；
即攻击臂 episode 级报警率 ≈ **69/216 = 0.32**（若以"注入在场"175 条为分母则 ≈ 0.39），
对照正常臂 58/672 = 0.086。这是安全审稿人会拿去用的数字，而它不在报告里。

同时，**"检出的都是已经成功的攻击"这一操作性后果没有被写出来**：对没有执行的 77 条
（56 有界抵御 + 21 静默）攻击 episode，检测器基本处在校准水平（0.143 / 0.095）。

**修**：§6.3 前加一张**漏斗表**（216 → 128 → 72 → 71 → 59 视界内），并在同一处报出
攻击臂整体报警率 69/216 与正常臂 58/672；摘要里把 0.746 的分母口径用半句话说清
（"在**已经产生执行事件且窗口可达**的攻击 episode 上"）。

## 2. SHOULD-FIX

### R7 — S 唯一输掉的那次比较，工作点对 S 有利，而且细节被压缩了

**位置**：§6.3 次级判定表 S2 行。

报告给 H1 的信息是完整的（b = 21 / c = 2 / both 32 / neither 16，两侧 FAR **逐位相等** 0.0994264）。
给 S2 的只有 Δ、CI、p。源 `g_conf_confirmatory_report.md` 第 116 行还有两件正文没写的事：

1. **b = 4 / c = 3 / both = 49 / neither = 15** —— S 与 M 在 71 个 episode 上**有 64 个（90%）判定相同**，
   Δ_SM = 0.014085 就是 **1/71**；
2. **`FAR_M = 0.0936902`，而 `FAR_S = 0.0994264`** —— 与 P 不同，**M 的工作点并没有真正匹配上**
   （匹配规则是"实测 FAR ≤ 目标的最大 α"，M 落在了下方）。**即 M 是在更低的误报率上打平 S 的。**

外部读者的结论会是：**本文精心设计的稀有坐标 surprisal，相对一个朴素的白化选择率距离没有可测的增量，
而且这个"打平"还是在对 M 不利的工作点上取得的。** 摘要里的"S2 不成立"没有传达这一层。

**修**：S2 行补上 (b, c) 与 `FAR_M`；在 §6.3 或 §9 加一句「**S 相对 M 的增量在 G-conf 上不可测，
且 M 的匹配工作点实测 FAR 更低**；本轮的确认只支持"selection 几何有效"，不支持"稀有掩码是必要的"」。

### R8 — "几乎逐位命中开发集先验中心 0.264" 是过度解读

**位置**：摘要、§6.3 判定块下的引文。

Δ̂ = 0.2676 与先验中心 0.264 相差 0.004，而同一行给出的 CI 是 **[0.071, 0.459]**（宽 0.39）。

### R9 — 摘要不能独立成立

**位置**：摘要（一段约 1 100 字，无分段）。

摘要**没有说**的关键事实：
- 数据是**场景工厂合成的模拟客服环境**，不是生产流量（读者极可能默认是真实 agent 日志）；
- 标注**全部由 LLM 完成，没有任何人工校验样本**（§9.8 才说）；
- **没有跑任何非路由基线**（R1）；
- 第一轮"确认性实验"是在**开发批 G-dev** 上做的（R10）；
- 判定所依据的配对样本只有 **71 条**，而摘要开头的规模数字是 **2 428 / 2 934**（R22）。

摘要**用到但未定义**的符号：`look`、`band`（虽未出现但"严格命中"出现）、"配对命中率"、
"家族聚类 CI"、"实测误报率匹配"、`prob_js`、`N1`、`F1`、"折 0"、"出厂门"、"两阶段解封"。
对一个只读摘要的审稿人，其中至少 `N1` / `F1` / `折 0` 是完全不可解的（它们是内部门编号）。

**修**：摘要拆成 4 段（问题 / 数据与纪律 / 结果 / 边界）；把 `N1`/`F1` 换成自然语言
（"正常臂质量过滤通过率不达标"、"折间可交换性检查在一折上超差"）；补上合成数据、LLM 标注、
无外部基线、N = 71 四句话。

### R10 — "确认性"一词有两个互相冲突的含义

**位置**：摘要"两轮预注册的确认性实验"、§5 标题与 §5.2、§6.3。

第一轮的权威来源文件名就叫 `g_dev_confirmatory_report.md`，而 G-dev 是**开发批**；
v3.2 又是**在同一批 G-dev 上开发出来的**。摘要"两轮预注册的确认性实验"会让读者以为
有两次独立确认，实际上只有 **G-conf 一次**是封存批上的确认。

同时，报告没有正面讨论一个审稿人一定会提的问题：**"预注册 → 失败 → 重写预注册 → 成功"这一流程，
整体的一类错误没有被控制**；被控制的只有第二轮在封存批内部的错误率（合取规则上界 0.036）。

**修**：(a) 全文把第一轮统一叫"**开发批上的预注册判定（v3.1）**"，把"确认性"保留给 G-conf；
(b) §4 或 §9 加一句：「两轮预注册之间的多重性没有被控制；**本文的错误率声明只覆盖 v3.2 在 G-conf 上的一次判定**」。

### R12 — 没有说清楚 G-conf 到底"留出"了什么

**位置**：§3.2 最后一句、§6.3。

§3.2 只写了 G-conf 的构成（`core_72_cells` 144 × 3 臂 + `held_out_workflow` 16 × 3 臂 +
`normal` 120 × 2 臂，16 个攻击家族，独立 fixture TSL/WRH/OSY），**没有告诉读者**：
G-dev 用的是**同一套 72 个设计格和同一批 16 个攻击家族**（源 `g_session_medium_conf_run_log.md` 第 404–412 行；
G-medium 甚至复用 G-dev 的 fixture）。也就是说，**封存批留出的是 fixture（表层实体）与 16 条新 workflow，
不是攻击家族、不是场景设计格。**

后果：外部读者会把 G-conf 当成"独立的新分布"，而它更接近"同一设计下的第二次抽样"。
而**唯一真正的泛化分层——`held_out_workflow` 9/10 = 0.9000（源 §5.4）——正文没有报**。

### R13 — FAR 的分母在全文中切换，且大多没有标注

### R14 — 0.806 与 0.746 并列出现却没有说它们是两个不同的量

**位置**：§6.6「有界抵御是 F4 语义的正面对照」条。

### R16 — 完全没有讨论自适应攻击者

说明"一个数量级"的来历，或把这句话降级为"至少"。
