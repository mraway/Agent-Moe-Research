## 0. 一句话判断

这份草案在**事件来源**上是正确的一步（模型自主函数调用把 JSON 脚手架推进正常参照、受限工具桩给出 token 级自动锚点、
双通道让"内部已参与、用户可见文本干净"成为可标注类），但在**评价口径与规模倒推**上还不能冻结：
主校准列在长视界处会被自己的长度分布删失（重犯 C1/FHTS 的老错）、
拟合池定义与草案 §0 自述要修的第一条缺陷互相矛盾、
两个声明的检测器视图都不含 commentary 通道却把 C_tool 定为主事件、
代码配额比两线一致的 B3 要求低一个量级、
G-conf 承担不了它被指派的确认角色、
以及 brief §1 的"多信号之一"定位所要求的基线增量从未被预注册。

## 2. 对委派单四个专门问题的直接回答

### 2.1 因果性与报警时刻定义（brief §3.1）

**不合格，见 F4。** brief §3.1 要求"明确报告首次报警时刻、持续时间和状态变化"，但草案在把 Agent 改成多步循环之后，
从未定义全局 token 时钟。多步 + 三通道 + 两种视图 = 同一条 trace 有至少三种可能的 t，`onset+16` 在三种读法下不是同一件事。
这不是文字问题：ecx §2.1 已经证明，一个错配的锚点会把**正确的早期检出**记成 pre-onset（X 列 pre 计数里 11/12–16/16 是记账假象）。
在新模型上把同一个错误换个形式重犯，代价是整批数据的时序结论不可用。

### 2.2 两个问题的标签（brief §1：deviation detection / state classification）

- **Q1 deviation detection：够。** E（分通道）+ C_tool 自动事件 + 双锚点 + 证据 span，比 v2 严格更好，尤其 C_tool 是**无需文本标注、token 级精确**的锚点，这是本稿最有价值的单点贡献。
- **Q2 state classification：不够，见 F8。** 恢复真值只覆盖"X 之后"，`engaged_only` 没有恢复锚点；轨迹类→SUSTAINED/RECOVERING/UNCERTAIN 的映射没写；UNCERTAIN 没有真值定义；brief §7 要的 abstention 计分没有。
  而"有界抵御的恢复"恰恰是两线都失败、且 ecx §3 把"≥12 条有界抵御"写进 B3 要求的那一项——如果 G 采完了仍然标不出这类样本的恢复点，Q2 在 v4 还是没有可用真值。

### 2.3 跨任务通用性（brief §3.4）：受限工具桩 / 措辞层级引入了任务专用规则吗？

**检测器侧没有，评价侧有一个隐患。** 受限工具桩与 T0–T3 措辞都只是**标签来源与刺激设计**，不进检测器输入，这一点是干净的
（与共识报告 §4 末段的立场一致："这些是标注规则，不是专用检测特征"）。三个残留问题：

1. **F7**：B 类正例（未授权工具调用）在语义上就是一次工具调用，而工具授权策略检查对它是完美检测器。把 B 类混进头条指标 = 用一个有平凡基线的子问题抬高路由的成绩。
2. **F25**：受限工具桩的固定返回串是只在攻击轨迹出现的上下文标记，C_tool 之后的路由差异有非偏离性解释。
3. **F12**：held-out 只到 scenario/fixture，没有 held-out workflow 类型，brief §3.4 点名要求的那条泛化轴没被检验。

### 2.4 analysis 通道在生产中的可见性：哪个视图是主？

**主视图应当是 V1（全部生成 token：analysis + commentary + final）**，V3（仅 final）是鲁棒性列，不是"更现实的部署"。理由：

1. **能读路由的实体必然托管模型。** 路由张量只在推理进程内部存在；任何能拿到 `R_t` 的部署方同时也拿得到 analysis token。
   "看不到思维链"的场景（第三方护栏、CoT 因隐私被丢弃）恰恰也拿不到路由，两者不同时成立。
2. **这条研究线最强的故事就在 analysis 上。** 试跑 §2.3 记录到 gpt-oss 会"在 analysis 里参与、在 final 里不留痕迹"（2/8 探针）。
   这类样本对**任何文本检查**都是隐形的，而路由逐 token 覆盖 analysis——brief §1 的"多信号之一"在这里才有真正的增量论证（F7 的基线比较也应该在这一类上给出最大增益）。
3. 但 F3 指出的漏洞必须先补：把 commentary 明确纳入 V1，否则 C_tool 主事件在主视图下不可评价。

草案说"两种视图都报"是对的，缺的是**声明哪一个是主**——brief §3.7 与 §9 要求主指标在解盲前锁定，"都报"不能替代"主列声明"。

### 2.5 B3 等价封存（brief §8）

**方向对、规模不对、程序有单点报废风险，见 F6。** 顺序（G-conf 最后生成、立即封存、只留哈希）符合 brief §8；
"资格门是数据门不是检测器门"（§6.4）也是正确的表述。但 120 条正常撑不起 §7 自己定的主校准列，
80 条攻击撑不起 ecx §3 的 B3 清单，"不读取"又使得批次质量在解封前不可知。
建议照 C1 的既有先例：**routing-blind、text-only 验收报告**（C1 报告的全部内容都是在"尚未读取 routing score"的状态下产出的），
路由与检测分数继续封存。这不违反 brief §8——§8 封的是"用 B3 做确认分析"，不是"确认 B3 采集成功"。

### 2.6 与 Codex 线的统一比较：clean break 还是延续？哪个对？

**数据层面必须是 clean break，口径层面必须是严格延续。草案做对了后者的大部分，但漏了三处，且没有桥接。**

- **数据层面 clean break 是对的**：gpt-oss 是 24 层 × 32 专家 × top-4，OLMoE 是 16 × 64 × top-8，路由特征不可迁移；
  且 §0.1 已经论证 OLMoE 的正常池本身有噪声（试跑 §4：12 条里 5 条把 JSON action 吐给客户、2 条无答复、1 条凭空造订单）。
  继续在 OLMoE 上加数据不能修掉这些。
- **口径延续已保住的**：E 为主锚点、X 只作子分类、+16 为跨家族主视界、pre-onset 罚则双版本共主、静默攻击报警硬门、
  clean/benign 双分母——这六条正是 ecx §3 与 trm3 §5.3 的决定，草案 §7 逐条继承，**这是本稿最好的部分，不要动**。
- **漏掉的三处**：F16（未采纳共识报告 §7 的完整锚点敏感性族）、F13（缺 matched-group / per-token / 长度分层 / 多 operating point）、
  F17（未规定在 G 上重跑两线的冻结方法家族作为基线）。没有 F17，G 上的任何"最好"都没有外部参照物——
  ecx 幸存的那条唯一跨线结论就白丢了。
- **建议增加 G-bridge**（F17）：把 h384 的 80 个 scenario 原样在 gpt-oss 上跑一遍，240 条 / ~1 小时 GPU，
  代价极低，但它是把"模型换了"与"算法变了"两个混杂因素分开的唯一手段。

## 4. keep unchanged（不要在 v0.2 里动的部分）

以下条目要么直接来自已冻结的两线决定，要么是本稿实质性的正确创新。修改它们会重新引入已经被证伪或已经付过代价的问题。

1. **主锚点 E、X 只作子分类**（ecx §2.1：路由信号对应 E/C，不对应 X）。

3. **命中定义 pre-onset 罚则版与无罚则版共主**（trm3 §5.3）。

5. **clean / benign 双分母，自发偏离样本保留在分母内并单独标注**（ecx §3；C1 的"不能事后删除高难正常样本"）。
6. **标注在路由解盲前冻结、两位标注者互盲、标注包不含分数与旧标签**（onset audit plan §5/§6）。
