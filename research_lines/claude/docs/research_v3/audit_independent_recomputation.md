### 1.3 4 条自发偏离 trace 的排除

预注册 v1.1 修订 4 要求这 4 条 `goal_drift` benign_control 退出 routine 拟合、校准池与**每一个** FAR 分母。独立验证：

1. **FAR 分母**：h384 两列的 benign 分母都是 **76**（= 80 − 4），与 `result.json` 的 `benign_count` 一致；
   matched-group 分母仍是 80 组（这 4 条的 scenario 组还有 clean 成员）。
2. **校准池**（这一条是最强的独立证据）：conformal p 值只能取 `j/(n+1)`，所以 n 可以**从 p 值格点本身反解**。
   h384/D 反解得到 half0 的 n_ref = **76**、half1 = **80**。而这 4 条 trace 在 D 列的输出半份都是 **1**，
   即它们的 routine 成员属于参照半份 0——参照半份 0 正好少了 4 条。若未排除，两半都会是 80。
3. **永不进正例**：4 条的锚点都是 `None`。
4. 它们自身的描述性报警数（D 列 1/4、C1 列 3/4）与 `result.json` 的 `spontaneous_drift.any_alarm_count` 一致。

### 1.4 PROVISIONAL 从不计入 FAR

用 `p_fused <= 0.10`（CONFIRMED）复算得到的 FAR 与 `result.json` 逐位相同；若改用 `p_fused <= 0.25`（含 PROVISIONAL），
b2/D 的 pooled FAR 会从 **0.0750 变成 0.1875**，h384/C1 会从 **0.0641 变成 0.1603**。该检验有分辨力，且报告在正确的一侧。

### 1.5 视界删失只发生在 K_cal 之后

- 只有 **h384/C1** 一格有删失：62 条 trace / 6527 个端点，`censored_trace_fraction = 0.2583`、
  `censored_endpoint_fraction = 0.2101`——与 `result.json` 和报告 F6 完全一致。其余六格删失比例 **0.0**。
- 删失恒为**后缀**（无中间空洞），删失后 `p_fused` 冻结在最后一个视界内端点的值（逐条验证，误差 0）。
- 62 条被删失 trace 的最后一个视界内端点**全部是 `end = 191`**，视界内端点数**全部是 185**。
  这与 `K_cal = {S:185, M:185, J:189}` 的算术精确吻合：S/M 的第 185 个端点 = 7 + 184 = 191，J 的第 189 个 = 3 + 188 = 191。

### 1.6 没有 trace 被自己所在的校准半份打分

- 模式 D：三个目标上**没有任何 pair group 跨半份**；每个参照半份反解出的 n_ref **精确等于另一半份的 routine trace 数**
  （b2 80/80、b1 40/40、h384 76/80），这正是 `select_half` 的 `1 − group_half[g]` 语义。
- 更强的一条：若某条 routine trace 落在自己的参照集里，则 `#{Z ≥ R} ≥ 1` 恒成立，其 p 值**不可能**取到最小值 `1/(n+1)`。
  实测有 routine trace 取到 `1/(n+1)`（b2/D half1 2 条、b1/D half1 4 条、h384/D half1 2 条、C1 各半 2–4 条），
  证明这些 trace 不在自己的参照集内。
- C1 列：fit = fold 0（80）、calibration = folds 1–3（180）、held-out = fold 4（60，`fold_role = held_out_normal_evaluation`），
  三者互斥；四个 cell 的 `c1_heldout` 集合逐条核对**全部是 fold 4**。

## 3. 发现 2（minor）：h384/D 的匹配 α 对 B-M 比对 TRM-3 更严（方向对 TRM-3 有利）

h384/D 两个半份的参照规模不同（half0 n=76、half1 n=80），因此 TRM-3 自己花掉的可达预算是
half0 **0.090909**、half1 **0.086420**。而运行器把 B-M 的匹配 α 取成**两半的最小值 0.086420**并对全体 trace 使用。
于是在 half0 的 trace 上，B-M 被压到 0.0864，而 TRM-3 实际在花 0.0909。

报告 §1.5 把这两个数都列了出来（"0.086420（取两半最小）"），但没有说明这一不对称的方向。
它**偏向 TRM-3**（对手预算更小 → 更难报警 → TRM-3 更容易赢），因此 h384/D 的 net = −2 是一个
**保守**的失败：把 B-M 放回 half0 应得的 0.0909 只会让 net 更负。同理，b2/D 与 b1/D 两半 n 相同，无此问题。

## 6. 本审计方法的局限

`outputs.jsonl` 以 `--outputs primary` 生成，**只含 `trm3` 一个变体的行**。因此 B-M、A-S、A-J、A-SM/A-MJ/A-SJ
是我用同一批逐通道 conformal p 值**重新取阈**重建的（单通道 α = 0.10，两通道各 0.05）。
对 w = 8 的通道（M、S 及其组合）这是精确的——重建出的 FAR、召回、`onsets_per_1000` 与 `result.json`
在 18 个 cell 上逐位相同，这本身就验证了"`trm3` 行里的 `p_M` 就是 `m_only` 的 p 值"。
唯一的例外是 `j_only`（w = 4）：它自己的端点网格从 `end = 3` 起，比 `trm3` 的网格宽，
所以我为它算出的 `onsets_per_1000` 分母偏小约 4%（逐 trace 的报警判定仍然一致）。
**这是我的重建口径的产物，不是被审报告的问题**；`j_only` 也不在 P1 的路径上。

另外，`§7`（每 token 延迟 / 峰值内存）是计时量，无法从产物复算，未审。
